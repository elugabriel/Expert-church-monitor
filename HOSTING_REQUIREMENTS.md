# Hosting requirements: Expert Church Monitoring System on Render

Target: one Render web service plus one Render Postgres database, serving every church from
subdomains such as `rccg.expertchurch.com` and `penua.expertchurch.com`.

Prices and plan names change. Check Render's current pricing page before buying, and treat the
plan names in `render.yaml` as placeholders.

## 1. Accounts and things you must own

| Need | Why |
|---|---|
| Render account (with a payment card) | Hosts the web service and the database |
| GitHub (or GitLab) account and a private repo | Render deploys from Git |
| The domain `expertchurch.com`, with access to its DNS | Each church gets a subdomain |
| SMTP email account (optional) | Absentee emails. Gmail needs an App Password |
| eBulkSMS account with credit (optional) | Absentee, birthday and first-timer SMS, each sent by staff pressing Send |

## 2. Render resources

| Resource | Notes |
|---|---|
| Web service (Python) | Paid plan, so it never sleeps. Free plans sleep and wipe their disk. Start command: `gunicorn app:app --bind 0.0.0.0:$PORT` |
| Postgres database | Paid plan, so data is kept and backed up. Free Postgres expires. Link it through `DATABASE_URL` |
| Persistent disk (see section 5) | Needed unless member photos move into the database |
| Cron Job | Not needed: nothing is sent automatically |

`render.yaml` already describes the web service and database. Use **New > Blueprint** on Render.

## 3. Environment variables

| Variable | Required | Value |
|---|---|---|
| `DATABASE_URL` | Yes | Set automatically from the database by `render.yaml` |
| `SECRET_KEY` | Yes | Generated by `render.yaml`. Must stay the same, or everyone is logged out on each deploy |
| `BASE_DOMAIN` | Yes for subdomains | `expertchurch.com` |
| `SUPERADMIN_USERNAME` | Yes | Your choice. Set it so you are never locked out |
| `SUPERADMIN_PASSWORD` | Yes | A strong password. Used only on the first start with an empty database |
| `PYTHON_VERSION` | Recommended | Pin it (the app was tested on 3.10) so Render does not pick a newer one |
| `MAIL_SERVER`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM`, `MAIL_USE_SSL` | Optional | For absentee emails |
| `EBULKSMS_USERNAME`, `EBULKSMS_API_KEY`, `EBULKSMS_SENDER`, `EBULKSMS_DND` | Optional | For absentee SMS. Sender is at most 11 letters or digits |
| `FLASK_DEBUG` | No | Leave unset in production (gunicorn does not use it) |

Never put real keys in `.env.example` or in Git.

## 4. Domain and DNS

1. In Render, open the web service, then **Settings > Custom Domains**.
2. Add `expertchurch.com` (the superadmin address) and the wildcard `*.expertchurch.com`, so new
   churches need no Render change. Confirm Render's current wildcard rules for your plan.
3. At your domain registrar, create the DNS records Render shows (a CNAME for `www` and subdomains, an
   A or ALIAS record for the bare domain).
4. Wait for Render to issue the HTTPS certificates before sharing links, because the QR codes use the
   church's own HTTPS address.
5. In the app, give each church its Subdomain (Superadmin > Edit Church).

## 5. Gaps to close before going live

These are real problems in the code as it stands, found while preparing this list.

1. **Postgres driver is missing.** `requirements.txt` has no `psycopg2-binary`. Without it the app cannot
   connect to Render Postgres and will fail to start. Add `psycopg2-binary` to `requirements.txt`.
2. **Member photos are saved on the server's disk** (`static/uploads`). Render wipes that on every deploy,
   so photos would disappear. Choose one:
   - Attach a Render persistent disk to the web service, mounted at `static/uploads`. Simple, but it is a
     paid add-on and limits the service to one instance.
   - Store photos in the database, as church logos already are. Needs a small code change, and is the
     more robust option.
3. **Untested on Postgres.** Everything was tested on SQLite. The Postgres upgrade path for the new
   `attendance` rule is written but has never run. Do a trial deploy with test data first.
4. **Nothing is committed yet.** Render deploys from Git, so the work must be committed and pushed.
5. **Backups.** Confirm your Postgres plan includes backups, and know how to restore one.

## 6. Capacity and settings

- Expected load is light: a few hundred users across many churches. One web instance is enough.
- gunicorn runs with defaults (one worker, 30 second timeout). Absentee emailing sends in batches of about
  20 seconds to stay under that limit. If it feels slow, set `--workers 2 --timeout 60`.
- The app trusts Render's proxy headers (`ProxyFix`), so HTTPS links come out correctly.

## 7. Security checklist

- Strong superadmin password, changed after first login.
- `.env` and `church.db` stay out of Git (already in `.gitignore`).
- Rotate the SQLite Cloud API key that appears in `.env.example`.
- Login passwords are shown once and must be changed at first use (built).

## 8. First deployment, step by step

1. Commit and push the project to a private GitHub repo.
2. On Render: **New > Blueprint**, pick the repo, and fill in the two superadmin variables when asked.
3. Wait for the build, then open the `onrender.com` address and log in as the superadmin.
4. Create a test church with a subdomain and a test admin, and check the temporary password flow.
5. Add the custom domains and DNS records, then open `testchurch.expertchurch.com`.
6. Log in as the church admin there and confirm: login works, a member can be added, a photo survives a
   redeploy, the QR link uses the church's address, and a QR check-in and a special-program
   registration work from a phone.
7. Delete the test data, then create the real churches.

Plan options:

| Setup | Monthly total |
|---|---|
| Minimum: Hobby + Starter web + Basic 256 MB Postgres | about $13 |
| More headroom: Hobby + Standard web + Basic 1 GB Postgres | about $44 |
| Minimum plus Pro workspace (more domains, 7-day recovery) | about $38 |

Costs outside Render: the domain name (paid yearly to your registrar), SMS credits from eBulkSMS (check their
price list; blocked-DND numbers cost 2 units), and email (Gmail is free but has daily sending limits).

The free Render plans are not suitable: the web service sleeps after 15 minutes, free Postgres expires after
30 days and has no backups, and neither supports a persistent disk.

Wildcard domains (`*.expertchurch.com`) are supported and get automatic HTTPS. Render's docs do not say whether
every plan includes them, so confirm on a Hobby workspace before relying on it. The apex domain must also point
to Render.
